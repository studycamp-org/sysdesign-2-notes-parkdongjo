# 3단계
- 스트리밍 vs 일괄처리
	- 스트림 처리
		- 데이터를 오는 대로 처리하고 거의 실시간으로 집계된 결과를 생성하는데 사용한다.
	- 일괄 처리
		- 이력 데이터를 백업하기 위해 활용한다.
	- 람다 vs 카파 아키텍처 (그림 6.10)
		- 람다 아키텍처: 일괄 처리 경로와 스트리밍 처리 경로를 동시에 지원 → 유지 관리해야 할 코드가 두 벌이라는 단점
		- 카파 아키텍처(Kappa architecture): 일괄 처리와 스트리밍 처리 경로를 하나로 결합
			- 핵심: 단일 스트림 처리 엔진으로 실시간 데이터 처리와 끊임없는 데이터 재처리 문제를 모두 해결
		- 본 설계안은 카파 아키텍처를 따른다 → 이력 데이터 재처리도 실시간 집계 서비스를 거친다.
		```mermaid
		flowchart LR
		    subgraph LAMBDA["람다 아키텍처"]
		        direction LR
		        LIN[/입력/] --> LMQ[(메시지 큐)]
		        LMQ --> LB["일괄 처리 계층<br/>일괄 처리 엔진"]
		        LMQ --> LS["스트리밍 계층<br/>실시간 처리 엔진"]
		        LB --> LSV["서비스 계층<br/>서비스 백엔드"]
		        LS --> LSV
		        LQ[질의] --> LSV
		        subgraph LDS["데이터 저장소"]
		            LRAW[(원시 데이터)] ~~~ LRES[(결과)]
		        end
		    end
		    subgraph KAPPA["카파 아키텍처"]
		        direction LR
		        KIN[/입력/] --> KMQ[(메시지 큐)]
		        KMQ --> KS["스트리밍 계층<br/>실시간 처리 엔진"]
		        KS --> KSV["서비스 계층<br/>서비스 백엔드"]
		        KQ[질의] --> KSV
		        subgraph KDS["데이터 저장소"]
		            KRAW[(원시 데이터)] ~~~ KRES[(결과)]
		        end
		    end
		    LAMBDA ~~~ KAPPA
		```
	- 데이터 재계산 (이력 데이터 재처리, historical data replay) (그림 6.11)
		- 집계 서비스에 중대한 버그가 있었을 때, 버그 발생 시점부터 원시 데이터를 다시 읽어 집계 데이터를 재계산
		- 흐름
			1. 재계산 서비스는 원시 데이터 저장소에서 데이터를 검색한다 (일괄 처리 프로세스).
			2. 추출된 데이터는 **재계산 전용** 데이터 집계 서비스로 전송된다. → 실시간 처리 과정이 과거 데이터 재처리 프로세스와 간섭하는 일을 막기 위함
			3. 집계 결과는 두 번째 메시지 큐로 전송되어 집계 결과 데이터베이스에 반영된다.
		- 재계산 프로세스는 데이터 집계 서비스를 재사용하지만, 처리 대상 데이터는 다른 곳(원시 데이터)에서 직접 읽는다.
		```mermaid
		flowchart LR
		    LOG[로그 모니터] --> MQ1[(메시지 큐)]
		    MQ1 --> AGG[데이터 집계 서비스]
		    MQ1 --> DBW1[데이터베이스 기록 프로세스]
		    DBW1 --> RAW[(원시 데이터 데이터베이스)]
		    AGG -- "광고 수 (매 분 집계)<br/>클릭 상위 100개 광고 (매 분 집계)" --> MQ2[(메시지 큐)]
		    RECALC[재계산 서비스] -- "① 원시 데이터 조회" --> RAW
		    RECALC -- "②" --> AGG2["데이터 집계 서비스<br/>(재계산 전용)"]
		    AGG2 -- "③" --> MQ2
		    MQ2 -- 재계산 서비스 --> DBW2[데이터베이스 기록 프로세스]
		    DBW2 --> RES[(집계 결과 데이터베이스)]
		    QS["질의 서비스 (대시보드)"] -- 집계 결과 질의 --> RES
		    style RECALC fill:#555,color:#fff
		```
	- 세 가지 유형의 시스템 비교 (표 6.17)

| 구분 | 서비스<br>(온라인 시스템) | 일괄 처리 시스템<br>(오프라인 시스템) | 스트리밍 시스템<br>(실시간에 가깝게 처리) |
| --- | --- | --- | --- |
| 응답성 | 클라이언트에게 빠르게 응답 | 클라이언트에게 응답할 필요가 없음 | 클라이언트에게 응답할 필요가 없음 |
| 입력 | 사용자의 요청 | 유한한 크기를 갖는 입력. 큰 규모의 데이터 | 입력에 경계가 없음 (무한 스트림) |
| 출력 | 클라이언트에 대한 응답 | 구체화 뷰, 집계 결과 지표 등 | 구체화 뷰, 집계 결과 지표 등 |
| 성능 측정 기준 | 가용성, 지연 시간 | 처리량 | 처리량, 지연 시간 |
| 사례 | 온라인 쇼핑 | 맵리듀스 | 플링크(Flink) |

- 시간
	- 타임스탬프가 만들어지는 두 위치
		- 이벤트 시각(event time): 광고 클릭이 발생한 시각
		- 처리 시각(processing time): 집계 서버가 클릭 이벤트를 처리한 시스템 시각
	- 네트워크 지연이나 비동기 처리 환경(메시지 큐 경유) 때문에 두 시각 사이의 격차가 커질 수 있다 (그림 6.12: 이벤트 1이 5시간 뒤에 도착)
		```mermaid
		flowchart LR
		    subgraph ET["이벤트 시각"]
		        direction LR
		        E1(("① 10초")) --> E2(("② 50초")) --> E3(("③ 80초"))
		    end
		    subgraph PT["처리 시각"]
		        direction LR
		        P2(("② 65초")) --> P3(("③ 85초")) -.->|"…"| P1(("① 5시간 후"))
		    end
		    E1 -. 늦게 도착 .-> P1
		    E2 --> P2
		    E3 --> P3
		    style P1 fill:#f66,color:#fff
		```
	- 이벤트 발생 시각 vs 처리 시각 (표 6.18)
		```mermaid
		flowchart LR

		        direction TB
		        EVP["장점: 광고 클릭 시점을 정확히 아는 것은 클라이언트이므로 집계 결과가 보다 정확"] ~~~ EVC["단점: 클라이언트 타임스탬프에 의존 → 클라이언트 시각이 잘못되었거나 악성 사용자가 조작하는 문제에서 자유롭지 않음"]
		```

	- 데이터 정확도가 아주 중요하므로 **이벤트 발생 시각 사용을 추천** → 늦게 도착한 이벤트는 **워터마크(watermark)** 로 처리
	- 워터마크
		- 1분 텀블링 윈도에서 윈도 끝보다 살짝 늦게 도착한 이벤트(이벤트 2, 5)는 집계에서 누락된다 (그림 6.13)
			```mermaid

			    dateFormat X
			    axisFormat %M:%S

			    ② :milestone, 55, 0s
			    ③ :milestone, 75, 0s
			    ④ :milestone, 130, 0s
			    ⑤ :milestone, 175, 0s
			    section 처리 시각
			    ① :milestone, 35, 0s
			    ② (누락) :crit, milestone, 63, 0s
			    ③ :milestone, 72, 0s
			    ④ :milestone, 150, 0s
			    ⑤ (누락) :crit, milestone, 185, 0s
			    section 윈도
			    윈도 1 - ① :w1, 0, 60s
			    윈도 2 - ③ :w2, 60, 60s
			    윈도 3 - ④ :w3, 120, 60s
			```
		- 각 윈도 마지막에 여분의 구간(워터마크)을 붙여 집계 윈도를 확장한다 (그림 6.14)
			- 예: 15초 워터마크 → 윈도 1은 이벤트 2를, 윈도 3은 이벤트 5를 집계할 수 있게 됨
			```mermaid
			gantt
			    title 그림 6.14 워터마크 (15초)
			    dateFormat X
			    axisFormat %M:%S
			    section 처리 시각
			    ① :milestone, 35, 0s
			    ② :milestone, 63, 0s
			    ③ :milestone, 72, 0s
			    ④ :milestone, 150, 0s
			    ⑤ :milestone, 185, 0s
			    section 윈도 1
			    윈도 1 - ① :w1, 0, 60s
			    워터마크 - ② :active, 60, 15s
			    section 윈도 2
			    윈도 2 - ③ :w2, 60, 60s
			    워터마크 :active, 120, 15s
			    section 윈도 3
			    윈도 3 - ④ :w3, 120, 60s
			    워터마크 - ⑤ :active, 180, 15s
			```
		- 워터마크 크기는 비즈니스 요구사항에 따라 결정
			- 길면: 늦게 도착하는 이벤트도 포착하지만 이벤트 처리 시간이 늘어남
			- 짧으면: 데이터 정확도는 떨어지지만 응답 지연은 낮아짐
		- 한계
			- 시간이 한참 흐른 후 도달하는 이벤트는 처리할 수 없다 → 발생 확률 낮은 이벤트를 위해 시스템을 복잡하게 만드는 것은 ROI가 낮음
			- 사소한 데이터 오류는 하루치 데이터 처리를 마감할 때 **조정(reconciliation)** 으로 보정 가능
			- 정확도는 높아지지만 대기 시간이 늘어나 전반적인 지연 시간이 늘어난다.

- 전달 보장
	- 집계 결과는 과금 등에 활용되므로 데이터 정확성과 무결성이 중요
		- 이벤트 중복 처리를 어떻게 피할 것인가?
		- 모든 이벤트의 처리를 어떻게 보장할 것인가?
	- 카프카 등 메시지 큐의 세 가지 전달 방식: 최대 한 번(at-most once), 최소 한 번(at-least once), 정확히 한 번(exactly once)
	- 어떤 전달 방식을 택할 것인가
		- 약간의 중복이 괜찮다면 대체로 '최소 한 번'이 적절
		- 본 시스템은 몇 퍼센트 차이가 수백만 달러 차이로 이어질 수 있으므로 **'정확히 한 번'** 권장 (참고: Yelp 사례)
	- 데이터 중복 제거
		- 중복 발생의 흔한 원인
			- 클라이언트 측: 같은 이벤트를 여러 번 전송 → 악의적 중복은 광고 사기/위험 제어(ad fraud/risk control) 컴포넌트로 처리
			- 서버 장애: 집계 중 노드 장애로 업스트림에 ack를 못 보내면 같은 이벤트가 재전송되어 재집계
		- 중복 데이터 발생 과정 (그림 6.17)
			- 업스트림 카프카에서 오프셋 100~110 소비 → 집계 → 다운스트림 전송 → 수신 응답
			- 6단계(업스트림에 오프셋 110 응답) 전에 장애 → 복구 노드가 오프셋 100부터 다시 소비 → 중복
			```mermaid
			sequenceDiagram
			    participant U as 업스트림(카프카)
			    participant A as 집계 서비스 노드
			    participant D as 다운스트림(카프카)
			    A->>U: 1. 이벤트 수집 (폴)
			    U->>A: 2. 오프셋 100부터 소비
			    A->>A: 3. 100부터 110까지의 이벤트 집계
			    A->>D: 4. 집계 결과 전송
			    D->>A: 5. 수신 응답
			    A-xU: 6. 110까지 소비하였음을 응답 (장애로 실패)
			    Note over U,A: 6단계를 마치지 못하고 장애를 내면<br/>오프셋 100부터 다시 소비 → 데이터 중복 발생
			```
		- 해결 1: 외부 저장소(HDFS/S3)에 오프셋 기록 (그림 6.18)
			- 저장된 마지막 오프셋이 100일 때만 100~110 처리, 110이면 그 이전 이벤트는 무시
			- 문제: 다운스트림 전송(4단계) 전에 오프셋을 저장(3.2단계)하면, 그 직후 장애 시 100~110 이벤트가 **유실**됨
			```mermaid
			sequenceDiagram
			    participant U as 업스트림(카프카)
			    participant A as 집계 서비스 노드
			    participant S as HDFS / S3
			    participant D as 다운스트림(카프카)
			    A->>U: 1. 이벤트 수집 (폴)
			    U->>A: 2. 오프셋 100부터 소비
			    A->>S: 3.1 오프셋 확인
			```

- 데이터 모니터링 및 정확성
	- 집계 결과는 RTB(Real-Time Bidding) 및 청구서 발행에 쓰이므로 모니터링과 정확성 보장이 중요
	- 지속적 모니터링 지표
		- 지연 시간(latency): 중요 부분마다 타임스탬프 추적 → 기록 시각 차이를 지연 시간 지표로 모니터링
		- 메시지 큐 크기: 갑자기 늘면 집계 노드 추가 필요. 카프카는 분산 커밋 로그이므로 레코드 처리 지연 지표(records-lag) 추적
		- 집계 노드의 시스템 자원: CPU, 디스크, JVM 등
	- 조정(reconciliation)
		- 다양한 데이터를 비교해 데이터 무결성을 보증하는 기법 (은행과 달리 광고 클릭 집계는 비교할 제3자가 없음)
		- 매일 각 파티션의 클릭 이벤트를 이벤트 발생 시각 순으로 일괄 처리한 결과와 실시간 집계 결과를 비교
		- 더 높은 정확도가 필요하면 더 작은 집계 윈도 사용 (예: 1시간)
		- 일부 이벤트는 늦게 도착할 수 있으므로 배치 결과와 실시간 결과가 정확히 일치하지 않을 수 있음
		- 최종 설계안 (그림 6.28): 기존 구조 + 원시 데이터 DB와 집계 결과 DB를 비교하는 '조정' 컴포넌트 추가
			```mermaid
			flowchart LR
			    LOG[로그 모니터] --> MQ1[(메시지 큐)]
			    MQ1 --> AGG[데이터 집계 서비스]
			    MQ1 --> DBW1[데이터베이스 기록 프로세스]
			    DBW1 --> RAW[(원시 데이터 데이터베이스)]
			    AGG -- "광고 수 (매 분 집계)<br/>클릭 상위 100개 광고 (매 분 집계)" --> MQ2[(메시지 큐)]
			    MQ2 --> DBW2[데이터베이스 기록 프로세스]
			    DBW2 --> RES[(집계 결과 데이터베이스)]
			    RECALC[재계산 서비스] --> RAW
			    RECALC --> AGG2["데이터 집계 서비스<br/>(재계산 전용)"]
			    AGG2 --> MQ2
			```

- 대안적 설계안
	- 면접에서는 전문 소프트웨어 내부 동작보다 사고 프로세스와 트레이드오프 설명 능력이 중요
	- 광고 클릭 데이터를 하이브(Hive)에 저장 + 빠른 질의는 일래스틱서치(ElasticSearch) 계층
	- 집계는 클릭하우스(ClickHouse)나 드루이드(Druid) 같은 OLAP 데이터베이스로 처리
	- 구조 (그림 6.29): 로그 모니터 → 메시지 큐 → 위험성 통제 엔진(Risk Control Engine) → 하이브 / 클릭하우스
		- 고객 대상 애널리틱스 → 클릭하우스에 집계 결과 질의
		- 데이터 과학자 → 일래스틱서치에 질의
		```mermaid
		flowchart LR
		    LOG[로그 모니터] --> MQ[(메시지 큐)]
		    MQ --> RCE["위험성 통제 엔진<br/>(Risk Control Engine)"]
		    RCE --> HIVE[하이브]
		    RCE --> CH[클릭하우스]
		    HIVE --> ES[일래스틱서치]
		    CA["고객 대상 애널리틱스<br/>(Analytics)"] -- 집계 결과 질의 --> CH
		    DS[데이터 과학자] -- 질의 --> ES
		```
