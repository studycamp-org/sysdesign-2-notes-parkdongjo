
메시지 큐는 블록 사이의 통신과 조율을 담당한다.
- 결합도 완화
- 규모 확장성 개선
- 가용성 개선
	- 장애가 발생해도 다른 컴포넌트는 큐와 계속 상호작용을 할 수 있다.
- 성능 개선
	- 비동기 통신이 쉽게 가능하다
	- 응답을 기다리지 않고도 메시지를 보낼 수 있다.

# 1단계

- 기능 요구사항
	- 텍스트 메시지만 지원된다.
		- 멀티미디어 지원까지 되면 설계가 어떻게 되나?
	- 메시지를 여러 소비자가 수신하는 것이 가능해야한다.
		- 전통적인 큐는 한 소비자가 받아간 메시지는 지워버린다.
	- 생산된 순서 그대로 소비되어야 한다.
		- 전통적인 메시지 큐는 보통 소비 순서를 보장하지 않는다.
	- 데이터 보관 기능 2주
		- 전통적인 메시지 큐는 메시지 보관을 보증하지 않는다.
	- 메시지 전달 방식은 아래 모두 다 지원하는 것이 이상적이다.
		- 최대 1회
		- 최소 1회 (무조건 보장)
		- 정확히 1회
	- 로그 수집등을 위해 높은 수준의 대역폭을 제공해야 한다.
	
- 비기능 요구사항
	- 로그 수집등을 위해 높은 수준의 대역폭을 제공해야 한다.
		- 높은 대역폭과 낮은 전송 지연 가운데 하나로 설정 가능하게 하는 기능 필요
	- 규모 확장성
	- 지속성 및 내구성
		- 데이터는 디스크에 지속적으로 보관되어야 하며
		- 여러 노드에 복제되어야 한다.

	- 발행-구독
		- 토픽
			- 토픽은 메시지를 주제별로 정리하는 데 사용된다

		- 메시지 전달
			- 토픽을 구독하는 모든 소비자에게 전달

	- 토픽에 보관데는 데이터양이 서버 한대로 불가능할 때
		- 파티션 = 샤딩
			- 파티션
				- 메시지의 작은 부분집합
			- 브로커
				-  파티션을 유지하는 서버
			- 토픽을 여러 팥션으로 분할
			- 메시지를 모든 파티션에 균등하게 나눠 보냄
				- 같은 파티션 안에서는 메시지 순서가 유지된다 (FIFO 구조)
				- 메시지는 사용자 ID 같은 키를 붙일 수 있는데, 같은 키를 가진 모든 메시지는 같은 파티션으로 보내진다.
				- 키가 없는 메시지는 무작위
			- 구독자
				- 토픽을 구독하는 소비자는 하나 이상의 파티션에서 데이터를 가져온다

	- 저장소
		- 데이터 저장소
			- 메시지는 파티션 내 데이터 저장소에 보관
		- 상태 저장소
			- 소비자 상태가 저장된다
		- 메타데이터 저장소

# 3단계

중요한 결정들
- 회전 디스크의 높은 순차 탐색 성능 + OS에서 제공하는 적극적 디스크 캐시 전략
	- 디스크 기반 자료구조를 활용할 것
- 아무 수정 없이도 전송이 가능하도록 하는 메시지 자료 구조
	- 복사에 드는 비용 최소화
- 일괄 처리
	- 소규모의 I/O가 많으면 높은 대역폭을 지원하기 어렵기 때문

- 데이터 저장소
	- 설계 고려점
		- 읽기와 쓰기가 빈번하게 일어난다
			- 읽기/쓰기 는 대부분 순차적으로 일어난다
		- 갱신, 삭제 연산은 발생하지 않는다.
			- 저장된 메시지에 대한 삭제 연산이 발생하기는 한다.
	- 선택지
		- 데이터베이스
			- 읽기 연산과 쓰기 연산이 동시에 대규모로 빈번하게 발생하는 상황을 잘 처리하는 데이터 베이스는 설계하기 어렵다
				- ==🟡[의문] 왜 DB는 읽기/쓰기 둘 다 성능을 챙기기 힘든걸까?==
			- 각 데이터베이스 검토
				- 관계형 데이터 베이스
					- 토픽별로 테이블을 만든다
					- 메시지는 해당 테이블에 새로운 레코드로 추가
				- NoSQL 데이터 베이스
					- 토픽별로 컬렉션을 만든다
					- 메시지는 하나의 문서가 된다.
				- 벡터형 데이터 베이스
		- 쓰기 우선 로그(Write-Ahead Log, WAL)
			- 새로운 항목이 추가되기만 하는 일반 파일이다.
			- 활용사례
				- MySQL의 복구 로그가 WAL로 구현되어 있다
				- 아파치 주키퍼도 해당 기술을 활용
			- 지속성 보장이 필요한 메시지 -> 디스크에 WAL로 보관하는 것이 추천된다.
				- WAL 에 대한 접근 패턴은 순차적인 읽기/쓰기 이다.
				- 흐름
					- 새로운 메시지는 꼬리 부분에 추가된다.
					- 로그 파일 줄번호를 오프셋으로 사용한다(쉬운 방법)
					- 파일 크기가 무한정 커질수 없으니 세그먼트 단위로 나눈다.
						- 세그먼트 활용
							- 새 메시지는 활성 상태 세그먼트에만 추가된다.
							- 세그먼트 크기가 일정 한계에 도달하면,
								- 새로운 세그먼트를 만들어 활성화하고, 이전 세그먼트는 비활성화 한다.
							- 이전 세그먼트는 읽기 요청만 처리한다.
							- 디스크 용량 한계가 되면 오래된 세그먼트는 삭제해버릴수도 있다.
							- "사진 2> 데이터 세그먼트 그림"
			- 디스크 활용
				- 편견
					- 디스크는 느리다
					- 하지만
						- 디스크가 정말로 느려지는 것은 데이터 접근 패턴이 무작위 일때다
						- 그렇다면
							- 순차적 데이터 접근 패턴을 적극 활용하는 디스크 기반을 활용
							- RAID로 구성된 현대적 디스크 드라이브 활용
								- ==🟡[의문] RAID 로 구성된 디스크가 뭐야?==
						- 현대적 운영체제는 디스크 데이터를 메모리에 적극적으로 캐시한다.
- 메시지 자료 구조
	- 메시지 구조는 높은 대역폭 달성의 열쇠
	- 메시지가 큐를 고쳐 소비자에게 전달되는 과정에서 불필요한 복사, 값비싼 복사가 일어나지 않도록 해야한다.
		- ==🟡[의문] 값비싸고, 불필요한 복사의 예시는 뭐가 있어? 어떤과정에서 그렇게 불필요한 복사가 일어난다는거야?==
	- "사진 3> 메시지 데이터 스키마"
		- 메시지키

			- 키가 주어진 경우
				- hash(key) & numPartitions 공식으로 결정된다.
			- 키는 클라이언트에 노출되어서는 안된다.

			- 토픽 - 메시지가 속한 토픽의 이름
			- 파티션 - 메시지가 속한 파티션 ID
			- 오프셋 - 파티션 내 메시지의 위치
			- 타임스탬프
			- 크기
			- CRC - 순환 중복 검사

- 일괄 처리
	- 일괄 처리가 성능 개선에 중요한 이유
		- 운영체제로 하여금 여러 메시지를 한번의 네트워크 요청으로 -> 네트어크 왕복 비용 제거
		- 더 큰 규모의 순차 연산이 발생 -> 더 큰 규모의 연속된 공간 점유 -> 더 높은 디스크 접근 대역폭 달성
	- 어려운점
		- 높은 대역폭과 낮은 응답지연은 동시에 달성이 어렵다
			- 낮은 응답지연이 중요하면
				- 일괄 처리 메시지 양은 낮춘다
				- 디스크 성능은 다소 낮아 진다
				- 하지만, 어느정도 처리량을 늘려야하면
					- 토픽당 파티션의 수를 늘린다.
			- 높은 대역폭을 달성하려면
				- 일괄처리 메시지 량을 높인다
				- 더 큼직큼직하게 디스크에 읽기, 쓰기를 달성해서 접근 대역폭을 넒게 쓴다.
- 생산자 측 작업 흐름
	- 파티션에 메시지를 보낼 때,
		- 어느 브로커에 연결해야하나?
			- 라우팅 계층 도입
				- `적절한` 브로커에 메시지를 보내는 역할
					- `적절한` 브로커 == `리더` 브로커
				- 흐름
					- 생산자는 메시지를 라우팅 계층으로 보낸다
					- 라우팅 계층은 
						- 준비
							- 메타 데이터 저장소에서 각 파티션 사본의 분산 배치 정보를 읽어서
							- 라우팅 계층 캐시에 보관한다.
						- 전송
							- 메시지가 도착하면, 파티션의 리더 사본에 보낸다.
								- 브로커 하나에 여러 사본이 들어간다.
								- 리더 사본은 파티션 마다 정해진다.
								- 같은 파티션의 사본은  서로 다른 브로커에 둔다.
								- 브로커와 사본의 관계 표
									```
									            | broker 1 | broker 2 | broker 3 |
									------------+----------+----------+----------+
									partition 0 | LEADER   | follower | follower |
									partition 1 | follower | LEADER   | follower |
									```
						- 파티션 내
							- 사본은 브로커에 저장되어 있다.
							- 리더 사본이 메시지를 받고, 해당 리더를 따르는 다른 사본은 해당 리더로 부터 데이터를 받는다.
							- 충분한 수의 사본이 동기화 되면 리더는 데이터를 디스크에 기록
								- 데이터가 소비 가능한 상태가 된다.
						- 회신
							- 디스크에 기록이 끝나고 나면, 생산자에게 회신을 보낸다.
						- 설계안
							- "사진 4> 라우팅 설계 초안"
			- 설계 개선
				- 1차적인 설계의 한계
					- 라우트 계층을 추가하면서 네트워크 노드가 더 늘어나, 네트워크 전송 지연이 늘어난다.
					- 일괄 처리에 대한 부분이 고려되지 않았다.
				- 수정안
					- "사진 5> 라우팅 설계 최종안"
						- 생산자 클라이언트 라이브러리의 일부로 편입
						- 네트워크를 거칠 필요가 줄어듬
						- 생산자가
							- 어느 파티션에 메시지를 보낼지 결정하는 로직을 가질 수 있다. 커스텀 가능
						- 버퍼 메모리에 보관했다가, 목적지로 일괄 전송이 가능하다
							- ==🟡[의문] 근데 이건 이전 설계에서도 할 수 있지 않나? 단지 위치가 클라이언트냐, 라우트계층이냐의 차이 아님? 라우트계층에서 버퍼 메모리에 저장했다가 한꺼번에 보내는게,,, 하긴 라우트에서 메시지를 차곡차곡 쌓는다는게 이상하긴 하다. 받자마자 바로 보내는게 라우트의 역할인데.==
- 소비자 측 작업 흐름
	- "사진 5> 소비자측 메시지 흐름"
	- 푸시 vs 풀
		- 브로커가 데이터를 소비자에게 보낼 것이냐
			- 푸시
				- 장점
					- 브로커는 메시지를 받는 즉시 소비자에게 보낼 수 있다.
				- 단점
					- 소비자에게 큰 부하가 걸릴 가능성이 있다
					- 전송 속도가 관건 -> 소비자는 항상 그에 맞는 처리 가능한 컴퓨팅 자원 필요
		- 소비자가 브로커에서 가져갈 것이냐
			- 풀
				- 메시지를 소비하는 속도를 소비자가 정한다.
					- 메시지를 실시간으로 가져갈 지

										- 메시지 손실을 감수해야한다.

			- 토픽의 규모를 늘리거나 대역폰을 조정하거나
			- 가용성과 대역폭 사이의 균현을 맞추는
		- 흐름
			- 생산자는 브로커와 통신할 때 그 사실을 통지 받고
			- 소비자는 재조정을 시행한다.
		- 결론
			- 파티션 수의 조정은 생산자와 소비자의 안정성에는 영향을 끼치지 않는다.
- 메시지 전달 방식
	- 최대 한번
		- 메시지가 전달 되는 과정에서 소실되더라도 다시 전달되는 일은 없다
		- 지표 모니터링 등 소량의 데이터 손실을 감수 할 수 있는 시스템에 적합
	- 최소 한번
		- 같은 메시지가 한 번 이상 전달 될 수 는 있으나 메시지 소실은 발생하지 않는다.
		- 데이터 중복이 큰 문제가 아닌 시스템이나, 소비자가 중복을 직접 제거할 수 있는 시스템일 경우 적합
	- 정확히 한번
		- 구현하기 가장 까다로운 전송 방식
		- 사용자 입장에서는 편리하지만, 시스템의 성능 및 구현 복잡도 측면에서는 큰 대가를 지불
		- 지불, 매매, 회계 등 금융 관련 응용에는 적합하다.
